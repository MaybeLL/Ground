# 自包含的 Requirement 与 Issue 契约

<a id="contract-boundary"></a>

## 契约边界

核心要求必须写入已发布 Requirement/Issue，不只存在于 Confluence、工单、附件、图、源码注释或其他外部材料。开发者仅持有 Issue 及其绑定 Requirement，就应知道实现什么、保留/排除什么、如何验收。实现仍需仓库访问；自包含不等于复制代码库或所有引用文档。

删去参考访问后仍不丢失必需规则，该参考才是有效证据或背景。“按此 URL 实现”“selector 结构见子方案”“按文档处理错误”“通过链接验收矩阵”不能替代实际义务。链接本身不是问题，要判断承载的信息；不将强制行为隐藏在可选 Guidance 或来源注释。

<a id="extract-before-compressing"></a>

## 先提取，再压缩

读取请求范围相关来源；链接表格、附录或图若定义必需行为，也须阅读。记录来源身份和实际观察到的版本/日期/章节。按需沿链接解决核心规则，不递归阅读全部背景。工具截断、不可访问附件和未读页是覆盖缺口，不证明没有规则。不把文档作者声明当作仓库或生产验证。

每项可能影响实现/验收的来源要求，记录在草稿中的去向：Requirement Outcome/Decision/Context 或 Issue Goal/Constraint/Criterion。重要条件、输入/输出、单位、范围、顺序、默认值、零值与缺失、异常、兼容、验收样例应保留。保留区分正确/错误行为的细节；消除重复，不消除义务。

编写时使用简短的来源到契约覆盖表：

| 来源版本/章节 | 核心规则或未决决定 | 契约去向 | 处理情况 |
| --- | --- | --- | --- |
| 实际页版本、章节 | 实际规则，而非仅名称 | 已有 Markdown 标签或章节 | 已纳入 / 待澄清 / 明确超出范围 / 支持证据 |

表放在对话或已有 Workspace Context，不另建细化简报或存储实体。它是审计辅助，不替代契约规则。每项核心规则都需处理结论，“已链接”不算处理。范围排除基于已确认意图，不基于文档年代或便利性。发布契约保留简短来源版本引用，以区分后续变化与遗漏。

<a id="place-rules-at-the-right-level"></a>

## 将规则放在正确层级

- Requirement：业务目标、纳入/排除范围、共享业务规则、跨仓义务、关键决定和未决业务/协议问题。结构化细节放 Context，选择的规则放 Decisions，可观察结果放 Outcomes。
- Issue：仓库专属交付行为、输入/输出契约、相关边界/错误、强制约束和可独立判断 Criteria。用 Intent Links 追溯继承的 Outcomes/Decisions。可依赖绑定 Requirement 而不重复全文，但必须明确自身责任和 Criteria。
- Evidence/参考：原始来源、理由、历史观察，以及判断正确性不必需的说明细节。定义必需边界行为的样例也应进入契约。

不编造新字段或滥用 YAML 扩展承载缺失概念。已有 Markdown 章节支持正文、列表和明确 Criteria。真实字段/大小限制使契约无法完整保留时，报告具体限制并讨论拆分，不静默截断。Issue 只按已同意交付边界拆分，不仅为绕过限制。仅编写 Requirement 时，即便还没有 Issues，也保留已知共享规则，不完全留给假设的未来 Issues。

<a id="handle-missing-and-changed-evidence"></a>

## 处理缺失与变化的证据

已有契约比对绑定来源版本与新观察材料。分别标明：原范围遗漏、来源规则变化、来源矛盾、未验证实现声明。新页面不静默覆盖用户先前确认的决定或历史 Candidate 契约。实质变化先展示并确认，再修订；先解决上游决定，再封存受影响 Issues。

必需来源不可用或核心规则仍矛盾时，记录准确缺失决定及影响。每次只问一个阻塞问题并给建议，不猜默认值，也不因搜索失败宣称没有规则。仅发布 Requirement 可在约定范围保留 Open Questions；受影响 Issue 有未决假设或阻塞问题时不可作为可执行契约发布。遵循主 Skill 发布门禁。

<a id="two-checks-before-confirmation-and-publication"></a>

## 确认发布前的两项检查

1. **来源覆盖检查**：将所有发现的核心要求与去向比对，包括表/附录和异常路径。要求不能淡化为链接或可选 Guidance；排除范围与假设须明确。只读草稿无法发现来源遗漏，因此需要来源清单。
2. **脱离来源检查**：只看 Requirement 和每个 Issue 草稿，开发者能否不打开外部材料就区分允许/禁止行为并设计验收？仍需链接才能回答的规则，应复制到正确字段或明确列为未决问题。区分 Requirement-only 完整性与可执行 Issue 的完整性。

随拟定契约摘要报告有意义的缺口或已核对覆盖。不增加第二轮确认仪式：已有双方理解确认覆盖已审阅契约。CLI parse/dry-run 和关键词扫描不证明两项检查通过，也不增加普遍 URL 禁令。
