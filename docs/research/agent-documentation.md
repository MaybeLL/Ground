# 面向维护 Agent 的文档组织调查

调查日期：2026-10-30。状态：研究记录；部分建议已由独立规范采纳，本文本身不作为执行规范。

后续采纳说明：已新增[文档维护规范](../documentation.md)。该规范采用了后续讨论明确的分工：concepts 保存当前业务规则，architecture 描述当前实现，decisions 保存选择及理由。下文保留原始调查建议，不作为现行规则；架构正文、模块指南和检查扩展仍需按实际任务逐步补齐。

本文讨论维护 Grounds 源码的 Agent 如何获得项目上下文；不是向使用 Grounds 的 Agent 发布新的工作流。公开分支链接可能变化，案例反映调查时观察到的状态。以下区分公开实践、实验结果和本项目建议。

## 实验结果不支持“文档越多越好”

[Vercel / Jude Gao 的实验，2026-01-27](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)在特定 Next.js 16 API 任务集上报告：版本匹配文档的压缩索引达到 100% 通过率，显式提示调用的 skill 达到 79%。这是框架使用场景，不能直接等同于维护大型仓库，也不能推出固定大小索引或 AGENTS.md 总是优于 skill。

[Evaluating AGENTS.md，v3，2026-09-29](https://arxiv.org/abs/2602.11988v3)在其测试设置中发现，上下文文件总体未普遍改善任务成功率，平均推理成本增加超过 20%；建议严格评估效果。它考察具体文件、任务与 Agent，不能据此认定架构文档无价值。

二者可以同时成立：给出任务缺少的、版本匹配的知识可能有效，重复可从代码获得的信息或增加无关要求可能有害。Grounds 应用自己的任务验证组织方式。

## Grounds 当前情况

- [AGENTS.md](../../AGENTS.md) 已保持简短，提供代码区域、构建规范和关键安全约束；CLAUDE.md 是其相对符号链接，避免两套规则漂移。
- [CONTRIBUTING.md](../../CONTRIBUTING.md) 已要求用户可见行为改变时更新帮助、契约和指南；PR 模板也有文档更新检查项。
- [docs/README.md](../README.md) 有用户指南、契约、技能入口，但目前缺少维护者使用的领域概念图谱和架构导航。
- [插件 workflow skill](../../plugins/grounds/skills/grounds/SKILL.md) 是教 Agent 使用 Grounds 的产品内容，不能直接替代解释 Grounds 内部实现的维护文档。
- [文档检查脚本](../../scripts/check-docs.mjs) 已覆盖本地链接、锚点等检查，并支持特定历史设计记录的元数据校验。存在检查能力不等于已有完整知识库，也不代表语义准确性已经验证。
- 根 README 的 clone 地址已改为 Ground，部分其他入口和包元数据仍使用 grounds-open。旧地址虽会重定向，这仍是统一维护元数据的实际问题。

## 建议的文档职责

这是增量建议，不要求立即创建空目录或搬迁全部文档。

| 位置 | 职责 | 避免放入 |
| --- | --- | --- |
| README.md | 产品目的、使用场景、首次使用入口 | 维护全过程、完整内部约束 |
| AGENTS.md | 维护 Agent 的稳定规则和任务到文档的导航 | 长篇领域介绍、临时进度、所有模块细节 |
| docs/README.md | 人与 Agent 共用的知识导航 | 第二份完整操作手册 |
| docs/architecture.md | 组件关系、依赖方向、主要源代码入口、跨组件不变量 | 易变的逐函数说明 |
| docs/concepts/ | 领域术语、状态转换、业务不变量 | 每个命令的参数表 |
| 模块 CONTRIBUTING.md 或 docs/development/ | 模块修改流程、测试选择、局部限制 | 根规范的重复副本 |
| docs/contracts/v1/ | 版本化接口契约 | 尚未批准的设计设想 |
| docs/decisions/ | 决策背景、取舍、状态与替代关系 | 不加标记的未来行为 |
| docs/research/ | 外部调查、证据与建议 | 默认生效的开发指令 |
| plugins/grounds/ | 产品对外提供的 Agent 技能和配套资料 | 仅维护本仓库所需的私人上下文 |

typescript/README.md 和 tui/README.md 同时随包发布，应保留包用户入口职责。内部细节可放独立维护文档，再链接过去。只有确实存在局部执行规则时，才增加模块级 AGENTS.md；不同宿主自动发现行为应实际验证，不能仅凭文件存在推定已经加载。

## 建议采用的约束

1. **导航先于堆积内容。** 根入口用“任务 → 首读文档 → 源码/测试入口”指引。维护账本、调整 TUI、修改技能应有不同阅读路线。首次进入陌生模块读取对应维护文档；之后按任务变化补读。
2. **知识共享，指令分层。** 产品事实、架构和概念供人和 Agent 共用；执行要求放指导文件。新增局部规则说明作用范围和原因，不复制根规则。
3. **一项知识只有一个维护来源。** 文档可引用同一事实，但不要独立维护多份参数表。确需随插件分发的契约副本，应明确来源和同步流程，并检查一致性；本次未对全部副本的同步关系作完整审计。
4. **当前事实、目标规范和历史方案分别标记。** 重要决策记录 proposed / accepted / superseded 等状态和替代入口。代码与 accepted 契约冲突时记录差异并调查，不能为了消除冲突自动把文档改成当前代码行为。
5. **把隐含约束写出来。** 每个重要模块说明职责、依赖边界、业务不变量、典型修改入口和最小有效验证。例如解释“归档成功”“验证通过”“选择候选”“实际交付”的区别。
6. **链接证据，少复制实现。** 优先指向稳定文件、符号、契约和行为测试；记录外部案例时带版本或调查日期。不要把容易漂移的行号当唯一定位方式。
7. **变更与知识同时交付。** PR 指明受影响的概念、契约、操作指南和设计决策；不涉及文档时简要说明理由。只更新链接或日期不能当作语义复核。
8. **检查与风险相匹配。** CI 校验链接、生成内容、必要元数据和契约分发一致性；关键公开操作例子做可执行验证。文档是否准确解释业务、是否漏掉重要约束，仍需语义评审。
9. **入口有预算，但预算不是质量目标。** 可先给根 AGENTS.md 约百行的软预算，超过时审查是否应下沉；不要通过压缩成难读文本追求行数，也不要把预算说成行业标准。
10. **持久知识独立于会话。** 已确认的约定和设计理由进入公共文档；个人路径、凭据、私人验收材料和聊天过程不得混入。继续遵守仓库现有共享进度记录规则，不创建 PROCESS.md。

文档状态元数据优先用于架构、决策等容易被误解的材料，不要求每个短指南都填写同一套复杂表头。检查日期只表示何时复核，不自动证明事实正确。

## 实施次序和验证方式

第一步：先写一份文档维护规范和最小架构/领域导航，从 AGENTS.md 链接；统一仓库地址，列明产品技能与维护文档的边界。

第二步：针对 CLI、TUI、插件各补一个维护入口；按已发生的错误提取少量关键不变量和设计决策，避免自动生成大批源码摘要。

第三步：扩展现有文档检查，并增加少量任务验证。固定同一个源码 revision、Agent/模型和任务，比较有无新导航时的源码定位正确率、修改正确性、约束遗漏、读取量和耗时；重复试验以减少偶然性。至少覆盖账本行为变更、TUI 修正、契约/技能联动三类任务。不能只凭文档数量、token 数或 Agent 自评判断成功。
